Copilot: The bug was in the frontend. It only happened in **new conversations**, and it had nothing to do with tool calls.

**What happened**

1. When you start a new chat, `conversationId` is `null`. The `sendMessage.pending` reducer stores the user message under a temporary key, `local-<requestId>`, and streamed tokens go into `latestAiMessage`. So far, so good.
2. When the stream ends, the thunk in `conversationSlice.js` worked out the temporary key like this:
   ```js
   const isTemporary = conversationId?.startsWith('local-')        // null?.startsWith → undefined
   previousConversationId: isTemporary ? conversationId : null      // → null
   ```
   It checked the original `null` argument, not the `local-…` key that `pending` had actually used. So `previousConversationId` was always `null` for a new chat.
3. Because of that, `sendMessage.fulfilled` looked for messages under the real server ID. Nothing was stored there yet, so it fell back to `[]`, a new array that isn't part of the Redux state. The assistant message was pushed into that array and lost.
4. The reducer then reset `latestAiMessage` to `null`, so the streaming div disappeared. Nothing replaced it, because the final message had gone into the lost array. `currentChat` also stayed on the old `local-…` key.

**The fix**

The thunk now builds the key once, the same way `pending` does, and uses it everywhere:

```js
const chatId = conversationId ?? `local-${requestId}`
const isTemporary = chatId.startsWith('local-')
...
previousConversationId: isTemporary ? chatId : null
```

Now `fulfilled` moves the messages from `local-…` to the real conversation ID and adds the assistant message there.

I tested this by running the new-chat flow through the reducers in Node (pending → tokens → fulfilled). Both the user and assistant messages end up under the real ID, and `currentChat` switches to it. I haven't tried it in the browser yet.

My earlier backend fix still matters, but for a different problem: when the model called a tool, saving the message to MongoDB failed and the stream stopped partway through. That wasn't what made the message disappear at the end of streaming.
